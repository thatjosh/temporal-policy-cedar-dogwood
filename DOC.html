Agentic temporal policy constraints in Cedar and Dogwood

Executive summary

If you are putting a policy engine in front of an agent's tools, Cedar is the usual choice. In the agentic setting it has one structural gap: a Cedar policy judges one request at a time. An overeager agent can make requests that are individually compliant but that add up to a misbehaviour, so a policy has to remember what an agent has already done in order to police it. That is a temporal constraint.

Cedar was not built to be stateful, so a temporal constraint is not a first-class citizen in it. In this document we walk you through how you write one anyway, and why that turns out to be painful. That pain is why AWS introduced Dogwood, and we write the same rule there to see what changes. We close with what Dogwood does not fix: it has constraints of its own, and any design using it has to treat the log as a first-class citizen, which also changes how you test.

9 August 2026  ·  Assumes familiarity with Cedar policies and conditions. Both implementations were built and run: one rule, two engines, the same test suite. Every measurement quoted is from a run.

01

Policy design has to account for agentic behaviour, and that means temporal constraints

Imagine an agent whose job is to approve customer claims automatically. You're cautious about what it can do unsupervised, so you add a rule: anything over $100 escalates to a human. The claims tool enforces it: any single payment above $100 is denied.

That feels like a good control, and it is, right up until the agent becomes overeager. Handed a $500 claim it cannot pay in one go, it splits the claim into five payments of $100 and pays each one. Every payment is inside the limit. Every payment is approved. The escalation never happens.

Why the agent behaved that way is a separate investigation, and not the one that fixes this. What matters is how you design a policy that an overeager agent cannot get through.

The policy engine was asked, five times, whether a $100 payment was allowed, and five times it answered correctly. It was never asked whether $500 had already gone out. That is not a question about a payment. It is a question about the payments before it, and a rule that sees one request at a time cannot bound what a sequence of them adds up to. To close that, the control has to change shape: not is this payment allowed, but is this payment allowed given everything already paid.

That second rule is temporal, and it needs something a policy engine is usually built not to have: memory. Most engines remember nothing: you hand them a request, they judge that request, and nothing carries over.

Cedar is that kind of engine, and it is what most teams reach for today. The rest of this document is about adding a temporal constraint to it: how you do it, why it is more painful than it looks, and what Dogwood changes by moving the memory inside the engine.

02

Cedar keeps the engine stateless, so you hold the state yourself

Cedar is AWS's open-source authorization language. It has a schema, a validator and a real test story, and the rule from section 1 (no single payment over $100) is a single short policy. That part is genuinely easy, and it is why Cedar is the default answer when someone asks what should sit in front of an agent's tools.

Then you try to add the rolling-hour rule, and it stops being easy. Not because the syntax is hard. Because you cannot write the rule. You write part of it in the policy and the other part in your application logic, and from then on the rule only holds if both halves agree.

The reason is one property: a Cedar decision is stateless. It is a pure function of three inputs, the request, the policies and the entity store, and nothing in that tuple is history. It cannot look anything up, and it has no count or sum.

This is deliberate. Statelessness is what lets a policy set be checked by an SMT solver without running it, and Cedar lists that analysis as a design goal. The datetime extension shows how far that goes. It was accepted and shipped, and even so a currentTime() function was turned down inside it, on exactly this ground.

"However, currentTime() is stateful, i.e. not pure, and cannot be modeled in SMT."

Cedar RFC 0080, datetime extension. Accepted 11 September 2024, released 21 January 2025 in cedar-policy v4.3.0.

So a temporal constraint in Cedar is possible. It just stops living in one place. You keep the engine stateless and make the input stateful: your code queries your ledger, sums what was paid on this order in the last hour, and hands Cedar that number as a fact on the request. The policy compares it to the cap.

That split in full. First the rule as the engine sees it, then the code that feeds it:

cedar/v2/policy.cedar · the rolling-hour rule, comments removed

@id("rolling-hour-cap")
forbid (
  principal,
  action == Action::"pay",
  resource
)
unless {
  context has at &&
  context has amount_cents &&
  context has window &&
  context.window has order &&
  context.window has start &&
  context.window has total_cents &&
  context.window.order == resource &&
  context.window.start == context.at.offset(duration("-60m")) &&
  context.amount_cents <= 10000 &&
  context.window.total_cents >= 0 &&
  context.window.total_cents <= 10000 &&
  context.window.total_cents + context.amount_cents <= 10000
};

cedar/v2/ledger.py · the window and the sum, excerpted

WINDOW = timedelta(minutes=60)

def window_total(self, order_id: str, at: datetime) -> WindowTotal:
    start = at - WINDOW
    total = sum(p.amount_cents for p in self._payments
                if p.order_id == order_id and p.at >= start)
    return WindowTotal(order_id=order_id, start=start, total_cents=total)

Green is the rolling-hour rule. Three lines of it are in the policy: scope the total to this order, define the window, test the total against the cap. The rest is ledger.py, green in full because none of it existed before. Both blocks are one rule, and the payment is only judged correctly if both are right.

You now own and maintain that module. And the sixty minutes appears in both files, as timedelta(minutes=60) where the window is built and duration("-60m") where it is checked. They have to agree about what an hour is, and nothing but you enforces that. And that cost is paid per rule: the next temporal constraint splits the same way, with its own aggregation and its own pair of definitions to hold in step.

03

Dogwood moves the state into the engine, so the whole rule fits in one policy

In section 2 the rule ended up in two places: the window and the sum in ledger.py and the threshold in policy.cedar. Dogwood puts it in one. It is a temporal superset of Cedar that AWS open-sourced on 6 August 2026: the same language, plus a kind of clause that can read an event log. That makes the rolling-hour cap something the policy can state by itself.

Concretely, it is one clause appended to the per-payment rule you already have. No new module. The sixty minutes is written once, here, because nothing else needs to know it.

dogwood/v2/pay.dw · the clause appended to the existing rule, comments removed

when temporal {
    exists (total: Long). (
        sum_within(a, 1h, Support::Action::"Pay"::request{
            callerResource: resource,
            input.amount_cents: a
        }) == total
        && total <= 10000
    )
};

Set that against Cedar, where the same rule needed a policy and a module beside it. The difference is not brevity. There is no second half to keep in sync with.

04

The policy now reads your log, so a gap in it silently removes the rule

Section 2 said a Cedar decision is a pure function of the request, the policies and the entity store. A when temporal clause breaks that: it depends on a log, an input the engine reads, does not own and cannot check. So designing with Dogwood means treating the completeness of that log as a first-class concern, on the same footing as the policy itself. When the log is wrong, the rule fails silently.

The engine has nothing but the log to evaluate against. That is the side effect of making it stateful: a payment that never reaches the log did not happen, as far as the rule is concerned. Take three payments on one order inside the hour, against the $100 cap: $50 at 12:00, $30 at 12:10, and $40 arriving at 12:20 to be decided.

Nothing about that looks like a failure. A sum over fewer rows is just a smaller number, and the run exits 0.

Most logging pipelines are not built to carry a control. They sample, they buffer, and they drop under load, because for dashboards that is an acceptable trade. It stops being acceptable once a policy is reading them.

05

A rule that lives in one file can be unit tested; a rule split across two cannot

This section is about how to test a rule once it has a temporal constraint in it, and the difference between the two engines comes straight from section 3. Adding the rule gives you two components instead of one, in both. In Cedar they are the code that aggregates and the policy that compares; in Dogwood, the log and the policy that reads it. What differs is whether the rule spans both of them.

In Cedar the two halves are coupled by construction. Sixty minutes is written in both files, so changing the window means editing both. The policy checks that the window it was handed claims to start sixty minutes before the request; it cannot check what was actually summed. A ledger that sums thirty minutes and reports sixty passes every policy-level assertion, and so does one that always returns zero. You cannot write a clean unit test for this rule. You need a test that runs the two components end to end.

In Dogwood the rule is in one file. The window, the summation and the cap are all in the policy, so a test can hand it a log written by hand and check the answer, with none of your own code running.

06

Dogwood simplifies this, but only if logging is first class

To summarise what we have covered in this document: your agent has a tendency to misbehave. In our example, not by attacking anything but by breaking its task into steps that each satisfy the policy and together sidestep it. What you want is to gate it with a temporal constraint, a rule about what has already happened. Cedar was not built for that. Adding one brings complexity, because your change lands in two places: the policy, and the code that does the counting. You now have to keep both agreeing about things as basic as how long an hour is. Dogwood simplifies that, and on this evidence we would reach for it. The whole rule goes back into one place you can test on its own. But if you build on it, treat your logging as a first-class citizen. A record that never arrives will remove the rule with no error and a clean exit, and you will not hear about it.
